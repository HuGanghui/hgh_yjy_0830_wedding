# 祝福收集功能（留言板）—— 全过程复盘与架构说明

> 记录「扫码收集祝福 / 回信」功能从需求到上线的完整过程，并回答四个关键问题：
> ① 后端存储如何解耦、原理是什么；② 腾讯云 CloudBase 是什么、产品理念；
> ③ CloudBase Skill 能做什么、对我有哪些提效用法；④ 没「绑定」云函数，祝福是怎么写入数据库的。

---

## 一、功能全过程回顾

### 1.1 需求

扫码页原本只有单向流程：看公开照片/描述 → 输入收信码 → 解锁专属信件。没有**任何写回数据的机制**。
新需求：让扫码的朋友写下祝福/回信，新人日后能读到。

### 1.2 三项关键决策（用户拍板）

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 存储方式 | **云数据库直写（BaaS）** | 零服务器、纯静态页面，不想自建后端 |
| 放置位置 | **两处都放**：公开区「给新人的祝福」+ 解锁后信件视图「给收件人的回信」 | 无收件人条目也能送祝福；回信归属到具体收件人 |
| 展示方式 | **只收集、不回显** | 宾客永远读不到别人留言；新人到云厂商控制台查看/导出 |

### 1.3 存储抽象的由来

在动手前就明确了「**换后端零页面改动**」的诉求——所以先设计了 `provider + options` 抽象（见第二章）。
这个决策后来被证明至关重要：初选 LeanCloud 后不久，LeanCloud 就宣布**停服**（2026-01-12 发布公告，2027-01-12 数据销毁，且不再接受新应用），整个后端必须迁移。因为抽象层早已就位，迁移只是改 config + 换一个适配器，页面逻辑一行未动。

### 1.4 时间线与踩坑

1. **LeanCloud 方案**：完成适配器、文档、verify 测试（LeanCloud 版）。
2. **LeanCloud 停服** → 调研替代 → 选**腾讯云 CloudBase**（国内直连、微信扫码友好、免费额度够用、Serverless 文档库）。
3. **迁移实现**：build.js / index.html / config / verify / 文档 / 新增可部署云函数 `cloudbase/guestbook/`。
4. **踩坑一（术语/入口）**：把「Web 触发器」当成配置入口，但官方文档已迁移为 **HTTP 访问服务（云接入）**——控制台 → HTTP 访问服务 → 新建域名关联资源。全部术语随官方对齐。
5. **踩坑二（依赖缺失）**：云函数 `FUNCTIONS_INVOCATION_FAILED`，OPTIONS/POST 一起 400。特征指向**模块加载即崩** → 实锤 `@cloudbase/node-sdk` 依赖没装 → 补 package.json 并「保存并安装依赖」解决。
6. **踩坑三（集合不自动创建）**：函数通了，正常 POST 却返回 `500 写入失败`——文档数据库**不会自动建集合**，先建 `guestbook` 集合才能 `add()`。
7. **端到端验证**：curl 三连（预检 CORS / 写库 / 空文本 400）+ `scripts/verify.js` 587 项 + 本地浏览器冒烟 + 真机。
8. **上线**：提交产物 → push → GitHub Actions 自动部署成功。

## 二、后端存储如何解耦（核心设计）

### 2.1 为什么必须解耦

BaaS 厂商可能调整服务（LeanCloud 停服就是活例）。如果页面逻辑直接调某家的 SDK/API，换厂商 = 重写页面。
所以设计目标：**换后端 = 配置文件级改动 + 一个适配器条目，页面逻辑零改动**。

### 2.2 方案：`provider + options` 抽象（策略模式 / 依赖倒置）

三层结构：

**① config.json —— 声明用哪家、怎么连**

```json
"guestbook": {
  "enabled": true,
  "provider": "cloudbase",                    // 当前后端
  "options": {
    "url": "https://guestbook-....tcloudbase.com/guestbook"   // 该后端所需连接参数
  }
}
```

**② build.js —— 后端字段校验表（构建侧）**

```js
const GB_PROVIDERS = {
  cloudbase: { required: ['url'] }    // 每个后端声明必填字段
};
```

构建时按 `provider` 校验 options 合法性 → 产出 `public/guestbook.json`（浏览器读的客户端配置）。

**③ public/index.html —— 提交函数表（页面侧）**

```js
const GB_PROVIDERS = {
  cloudbase: {
    required: ['url'],
    submit(cfg, msg) {
      return fetch(cfg.url, { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify(msg) });
    }
  }
};
```

### 2.3 原理

> **页面只依赖一个抽象接口：「能把留言 POST 出去的 `submit(cfg, msg)`」**，不依赖任何具体厂商。

- `submitMessage()` 只负责构造 `msg = {type, entryId, to, name, text}`，再调 `GB_PROVIDERS[gb.provider].submit(gb.options, msg)`。
- `provider` 就是**接缝（seam）**：后端的一切差异（URL 拼法、请求头、鉴权方式）都被封在适配器里。
- 换后端 = ① GB_PROVIDERS 加一个适配器条目（build 与 index.html 各一份，必须同步）② config 换 `provider`/`options` ③ 新厂商控制台配好权限。**页面表单逻辑零改动**。

数据流：

```
浏览器扫码页 ──构造 msg──▶ GB_PROVIDERS[provider].submit(options, msg) ──fetch(POST)──▶ 云端写库
                                    ▲
                                    └─ 唯一需要知道厂商的地方（适配器表）
```

### 2.4 未来换 Supabase 的示例（文档化好的路径）

```js
// index.html
supabase: {
  required: ['url', 'anonKey', 'table'],
  submit(cfg, msg) {
    return fetch(`${cfg.url}/rest/v1/${cfg.table}`, {
      method: 'POST',
      headers: { 'apikey': cfg.anonKey, 'Authorization': `Bearer ${cfg.anonKey}`, 'Content-Type': 'application/json' },
      body: JSON.stringify(msg)
    });
  }
}
```

- build.js 加 `supabase: { required: ['url', 'anonKey', 'table'] }`
- config 换 options
- 控制台开 RLS「仅插入、禁止读」

## 三、腾讯云 CloudBase 是什么

### 3.1 是最近发布的新产品吗？——**不是**

- **2018 年 8-9 月**：腾讯云与微信联合推出「**小程序·云开发**」，是 CloudBase 最早的落地形态。
- **2019 年**：升级推广为「**云开发（TCB）**」，腾讯宣布 10 亿元扶持计划，到 2019 年底注册账号超 23 万、服务开发者超 50 万；2019 年 11 月从「0.1 时代」走向「1.0 时代」。
- 到今天（2026）已 **8 年**，是成熟稳定的老产品，不是新发布。

### 3.2 产品理念

CloudBase 的核心是 **Serverless（无服务器）**：

| 理念 | 说明 |
|------|------|
| **免运维** | 无需搭建/管理服务器，只关注业务逻辑 |
| **按量计费、弹性伸缩** | 自动扩缩容，按实际用量付费 |
| **一站式后端云服务** | 云函数 + 云数据库（MongoDB 协议文档库）+ 云存储 + CDN 一体化 |
| **一云多端** | 小程序 / 小游戏 / App / Web / H5 全端覆盖 |
| **深融微信生态** | 免鉴权调用微信登录、支付等 30+ 开放能力 |

### 3.3 为什么适合本项目

- **国内直连**：宾客用微信扫码，访问国内节点快、稳定（对比境外 BaaS 的 CDN 被墙问题）。
- **免费额度够用**：免费体验版 3000 资源点/月（云函数调用 13.3 点/万次、数据库读写 200 点/万次）——几百条留言约千分之几的点数。
- **HTTP 访问服务**：纯 REST 暴露云函数，保持扫码页零依赖单文件的设计。

## 五、你没「绑定」云函数，祝福是怎么写入的（关键澄清）

### 5.1 数据流全链路

```
浏览器（扫码页 JS）
   │  POST  JSON（type/entryId/to/name/text）
   ▼
https://guestbook-....tcloudbase.com/guestbook     ← HTTP 访问服务地址
   │  网关（tcbgw）按「域名关联资源」路由
   ▼
guestbook 云函数（exports.main，校验非空/长度）
   │  @cloudbase/node-sdk（管理端身份）db.collection('guestbook').add({...})
   ▼
云数据库 guestbook 集合 ←──── 写入成功
```

### 5.2 「绑定」到底发生在哪一步

> **绑定发生在 HTTP 访问服务，不在数据库侧。**

- **函数与 URL 的绑定**：控制台 →「HTTP 访问服务」→ 新建「域名关联资源」（关联资源类型=**云函数** → 选 `guestbook`、触发路径 `/guestbook`）。这一步才把 HTTP 地址路由**绑定**到函数——所以访问 `.../guestbook` 会触发这个函数。
- **函数与数据库集合之间没有「绑定」操作**：不存在「把集合绑到函数」这种控制台设置。函数写库是**程序化调用**：`cloudbase.init({env: SYMBOL_CURRENT_ENV})` 让函数以**管理端身份**直连当前环境数据库，再 `db.collection('guestbook').add(...)`。
- **安全规则 `{"read": false, "write": false}` 只管客户端**：宾客对集合零权限（读不了也写不了）；而云函数走管理端身份，**不受客户端安全规则限制**——所以函数能写、客户端不能写，这就是「唯一写入口」的实现。

### 5.3 一句话总结

**路由绑定在「HTTP 访问服务」，写库靠「函数的管理端身份」——数据库侧不需要任何「集合-函数绑定」操作。**

（你在配置数据库时看到的「权限设置」是安全规则，不是绑定；它负责把客户端挡住，而不是把函数放进来。）

## 七、复盘要点 / 教训

1. **厂商锁定是真实风险**：`provider + options` 抽象的价值在 LeanCloud 停服那一刻兑现——换后端零页面改动。任何依赖外部 BaaS 的项目都应预留这条接缝。
2. **官方术语和入口会变**：「Web 触发器」→「HTTP 访问服务（云接入）」；动手前先查官方文档，别照旧教程。
3. **云函数依赖是最常见的坑**：`FUNCTIONS_INVOCATION_FAILED` 且 OPTIONS/POST 一起挂 = 模块加载即崩，先查 `package.json` 依赖是否安装（控制台要点「保存并**安装依赖**」）。
4. **文档数据库集合不会自动创建**：`add()` 前必须先建集合，否则写入 500。
5. **服务端强制力 jsdom 测不了**：安全规则/鉴权必须手动 curl 或真机验证一次，verify 里只测客户端侧行为。
6. **构建产物有随机性**：`data.json` 每次随机 salt/IV、secret 媒体随机文件名——`public/` 必须整体提交保持一致，别只挑着提交。
7. **云函数是「唯一写入口」的关键设计**：数据库对客户端零权限，一切写操作经函数校验后落地——比客户端直写安全得多，值得在文档里讲透。

## 八、待办需求：留言板语音输入（暂缓，未实现）

> 记录于 2026-08-19。需求已提出、方向已拍板、方案已预研，但**暂不实现**，先存档备查。

### 8.1 需求

留言板（公开「给新人的祝福」 / 解锁后「给收件人的回信」）当前只能**输入框打字**。
希望增加**语音录入**，方便宾客直接说话留言。

### 8.2 已确认的方向（用户拍板）

**语音转文字（speech-to-text）**：语音自动转成文字填进留言框，仍按**文字**提交——新人照旧在控制台看文字，**零后端改动**。
已排除「语音消息（录一段音频上传）」方案：需云存储 + 云函数改造 + 留言板数据结构扩展 + 播放 UI，改动显著变大。

### 8.3 预研方案（浏览器原生 Web Speech API，零依赖）

- **能力检测**：`window.SpeechRecognition || window.webkitSpeechRecognition`，不支持 → 麦克风按钮直接隐藏（默认 `display:none`，检测到支持才显示），功能静默关闭。
- **交互**：留言框旁加麦克风按钮，点按开始/结束聆听；两处表单（公开祝福 + 信件回信）各一个按钮，复用同一套逻辑。
- **参数**：`rec.lang = 'zh-CN'`；`interimResults = true`（说话过程实时上屏）；`continuous = false`（停顿即结束）。
- **文字拼接**：已有手打内容保留为前缀，识别文字拼在其后；尊重 textarea `maxlength=500`（程序赋值需手动 slice 截断）。
- **降级**：识别错误（无麦克风 / 权限被拒 / 网络不可用）→ 在留言框反馈行给出原因，可继续手打，绝不拦留言流程。

### 8.4 测试要求（日后实现时必做）

按 CLAUDE.md 工作规则，须在 `scripts/verify.js` 同步补自检冒烟，与代码一并提交：
- 在 `createDom()` 的 `beforeParse` 注入 mock `SpeechRecognition`（仿现有 `HTMLMediaElement` 打桩），支持测试手动触发 `onresult` / `onend` / `onerror`。
- 新增 `checkVoiceInput` 覆盖：不支持时按钮隐藏；支持时按钮显示；点按进聆听态；interim 实时上屏；final 落定；已有文字前缀拼接；错误提示且可继续手打；`maxlength` 截断。

### 8.5 风险 / 踩坑预判

- **国内安卓微信端识别可能失败**：Web Speech API 在 Chrome 内核走 Google 语音服务，大陆网络可能不通；iOS Safari / 微信走 Siri 服务可用。失败必须静默降级手打。
- **若要更可靠**：改走腾讯云 ASR（一句话识别 / 录音文件识别），经现有云函数 `cloudbase/guestbook/` 代理——需 API key + 调用额度，改动显著变大，且多一次网络往返。
- 语音转文字仍产出**文字**，写入 `guestbook` 集合的 `text` 字段——存储结构、新人查看方式均不变。

### 8.6 状态

**暂缓，仅记录。** 日后决定实现时：从 8.3 方案入手 → 按 8.4 补 verify 冒烟 → `npm run verify` + `npm run build` → 部署。
